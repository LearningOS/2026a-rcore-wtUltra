# lab5：并发、同步与死锁检测

实验日期：2026-10-26
对应章节：ch8

## 功能总结

本次实验补全了 `sys_get_time` 时间写回，并在多线程架构下实现了按进程启停的死锁检测功能（`sys_enable_deadlock_detect`）。在进程控制块中分别为互斥锁（Mutex）和信号量（Semaphore）维护银行家算法所需的 `Available`、`Allocation` 和 `Need` 状态矩阵；每次线程申请同步资源时先进行试探性分配，若无法找到使所有线程顺利完成的安全序列，则立即回滚试探状态并返回 `-0xDEAD`。

## 实现细节与踩坑记录

- **检测开关与后台状态维护**：`sys_enable_deadlock_detect` 仅接受 `0` 或 `1` 作为有效参数。即便进程当前处于关闭检测的状态，内核在线程创建、退出以及锁和信号量的申请与释放过程中依然实时维护资源矩阵，避免进程在中途开启死锁检测时丢失此前已经建立的资源持有关系。
- **银行家算法与安全序列判定**：检测时令工作向量 `Work` 初值等于当前 `Available`，循环寻找满足 `Need <= Work` 的未完成线程，找到后假设其执行完毕并将它的 `Allocation` 累加回 `Work`；只有所有线程都能标记为完成才判定为安全状态。若判定不安全，则仅回滚本次新发起的试探请求，绝不破坏进程原有的持有和等待状态。
- **阻塞获取与条件变量处理**：对于因资源暂时不足而需要阻塞的合法请求，在阻塞期间仅计入 `Need` 矩阵，直到该线程后续被唤醒并真正拿到资源所有权后，才将其从 `Need` 转移到 `Allocation` 中，不会把尚在等待队列中的申请误算为已持有。此外，条件变量 `Condvar` 内部隐式执行的释放互斥锁与重新获取互斥锁操作，也同样同步更新了死锁检测状态。

## 问答题

### 1. 多线程架构下主线程退出的处理

当主线程退出导致整个进程终止时，内核需要停止该进程下属的所有线程，取消它们在就绪队列、同步原语等待队列以及定时器唤醒队列中的登记，并释放各个线程的用户栈、Trap 上下文页、内核栈、TID、寄存器上下文与同步资源引用；在进程层面，还需释放用户地址空间与页表、清空文件描述符表、处理父子进程关系，并按 `waitpid` 语义保留必要的退出状态码。
需要注意，一个线程的 `TCB`（`Arc<TaskControlBlock>`）可能同时被进程的 `tasks` 表、处理器的 `current` 指针、全局就绪队列、互斥锁/信号量/条件变量的阻塞等待队列、睡眠定时器队列以及内核执行路径上的临时 `Arc` 变量所持有。如果主线程退出时仅仅清空了进程自身的 `tasks` 列表，残留在其他队列中的强引用不仅会导致内存泄漏，还会导致已退出的死亡线程在锁释放或定时器到期时被再次唤醒执行。因此必须同步清理这些队列中的引用，或者标记为“已终止”状态并在各处出队时严格过滤；同时，当前正在运行退出逻辑的线程不能边执行边释放自己脚下的内核栈，必须切换离开后再完成回收。

### 2. 两种 Mutex 实现策略对比（Mutex1 与 Mutex2）

- **`Mutex1`（非公平竞争）**：在解锁时先将 `locked` 置为 `false`，随后唤醒一位等待者；被唤醒的线程恢复执行后必须在 `while` 循环中重新尝试竞争锁。如果在被唤醒者尚未被调度上 CPU 之前有新到达的线程调用 `lock`，新线程可能会抢先拿走锁，导致刚刚被唤醒的线程再次阻塞，因此公平性较弱，在调度不利时可能引发饥饿。
- **`Mutex2`（直接移交所有权）**：在解锁时若发现等待队列非空，则保持 `locked = true` 不变，直接将锁的所有权移交给队首等待者并将其唤醒；等待者恢复后不再循环重新检查 `locked`，直接进入临界区，从而减少了重复竞争并严格符合 FIFO 顺序。
- **省去循环的前提与风险**：`Mutex2` 中“不循环检查”能够成立，完全依赖于严格的锁所有权直接移交协议以及可靠的阻塞/唤醒机制。如果系统中存在虚假唤醒、支持中途取消等待者、错误复用 TCB，或者在未真正移交所有权的情况下误唤醒了线程，就会把未获锁的线程当成持锁者直接放进临界区。此外，两种实现都必须在调用 `block_current_and_run_next` 切换上下文前释放掉锁内部的可变借用（`UPSafeCell`），并且保证锁状态检查与入队阻塞之间的原子性，绝对不能把 `unlock` 置 `locked = false` 和 `lock` 不循环检查这两种语义混搭使用。
